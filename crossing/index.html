fall-federate · cross-machine mesh test

Relay a signed message across two real machines — no server.

The honest gap this closes: every prior "mesh proven" in the estate was one laptop talking to itself. Here, two genuinely separate machines on two networks (put one on a phone hotspot — a real NAT) connect directly over WebRTC with only a public STUN server, and relay a message as a chain of per-hop-signed, hash-chained hops. No TURN, no signalling server, no backend. The latency and delivery are measured and checked against a claim registered in advance. Same logic the mutation gate proves — re-run it here.

Can this device run it?

WebRTC + in-browser Ed25519 are required for the signed-hop transport. WebGPU is optional — it is only needed if a node also runs a local AI model on-device; the transport proof does not need it.

      The ~2-minute run, step by step (for when a second device is here)

      1. On device 2 (a phone on its mobile hotspot is ideal — that's the real NAT), open https://sjgant80-hub.github.io/fall-federate/crossing/. Check the top says WebRTC + Ed25519 are green.
      2. On device 1, tap Device 1 — start it, then Make my code. Tap Share join link and send it to device 2 (Signal / WhatsApp / Messages / AirDrop).
      3. On device 2, open that link (it auto-fills), or tap Device 2 — join and paste the code, then Make my reply code. Tap Share reply and send it back to device 1.
      4. On device 1, paste that reply, tick "Device 2 is on a different network", and tap Connect & run.
      5. The signed hop chain relays and the results panel fills in with the measured latency, delivery, and the PASS/FAIL verdict against the pre-registered claim. Honest either way.

      Devices that work: any two with a modern browser that has WebRTC + Ed25519 — Chrome / Edge / Firefox on Windows, macOS, Android; Safari 17+ and iOS 17+ on iPhone/iPad. The top-of-page check tells you plainly if a device is too old. Two laptops, or a laptop + a phone on its hotspot, both work; the phone-on-hotspot pair is the truest test because a real carrier NAT sits between them.

      Questions

      Why no QR code to scan?

      A WebRTC signalling blob (the full network description with gathered candidates) is 1.5–3 KB. A QR that a phone camera can reliably scan tops out well below that. So instead of a QR that never scans — theatre — you send the code as a link (device 2 just taps it) or a paste, over any app you already trust. That's the honest, robust, offline path.

      Why is there a human in the loop (swapping codes)?

      That's the sovereign choice, not a shortcut. Automatic connection would need a signalling server that sees who's talking to whom. Manual signalling + public STUN means no server holds the mesh — the only outside party is STUN, which learns a rough network address and never your message. The human join is the feature.

      What exactly is a "hop"?

      One signed step in a relay. Hop 0 is the origin (it carries the message); each later hop is signed by the node that forwarded it and commits to the exact previous hop by hash. So a hop can't be reordered, dropped, duplicated, or forged into the middle without the chain breaking — and every signature checks against public keys alone.

      What if the two devices won't connect?

      Then delivery FAILS and the page says so. STUN-only can't always traverse two symmetric NATs, and we don't add a TURN relay — that would put a server back in the path. A failed connection is a real, reportable result about real networks.
